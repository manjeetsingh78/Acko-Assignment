Pulse - Working AI Prompt Log

This is a cleaned record of the prompts and instructions used while building Pulse.
The wording is intentionally written as project work, and decisions match the final
implementation and DECISIONS.md.


18 Nov 2026

[Prompt 1 - Understanding the problem]

I am building Pulse for the Acko DevOps assignment. Before writing code, study
the problem statement PDF, PLAN.md, DECISIONS.md and the starter kit README.

Explain in simple words who uses the system and what they need:
- on-call engineers need to know about failures and the incident timeline
- support needs a quick view of affected services
- customers need a public status page without internal details
- leads need availability and error-budget information

List all must-have features and identify anything in the mock-service kit that
could act as a hidden test case. Do not code yet.


[Prompt 2 - Initial design]

Based on the problem statement, draft PLAN.md. Keep it as Gate 1 material and do
not overwrite it later. Include my decisions, user questions, scope, basic system
diagram, database tables, main screens, test plan and working metrics.

The initial technology choice is Python FastAPI, PostgreSQL, httpx, SQLAlchemy,
Docker Compose and pytest. We are also starting with an API-only backend because
the product owner can decide whether a frontend is required.


[Prompt 3 - Product-owner questions]

Prepare the important questions for the product owner. The answers I need are
about:
- health-check interval
- timeout and slow thresholds
- how many failures open an incident
- how many successes close an incident
- whether multiple incidents can be open
- public information allowed
- notification payload
- data retention
- authentication
- priorities

For every question, say what I would change in the implementation depending on
the answer. Keep the choices practical for a one-day build.


[Prompt 4 - PostgreSQL change]

The product owner requested PostgreSQL instead of SQLite. Update the project
from SQLite to PostgreSQL 16. Keep history in a named Docker volume and use
PULSE_DATABASE_URL for configuration.

The database should expose a real test database named pulse_test on port 5433
in local Compose. The test suite should use Postgres rather than SQLite so that
constraints and SQL behavior match production.


[Prompt 5 - Docker skeleton]

Create the first working Docker setup. It should start the Pulse API, PostgreSQL,
quotes, payments, claims, notifications and the webhook receiver with:

docker compose up --build

The Pulse container must use service names from inside the Compose network,
for example http://claims:8080/health. Do not modify any starter-kit mock service
or webhook receiver file.

Seed the four services on first startup. Do not overwrite existing operator
edits when the application restarts.


[Prompt 6 - Configuration]

Add central configuration in app/config.py using environment variables.

Use these defaults:
- default interval critical 10 s
- high 15 s
- medium 20 s
- low 30 s
- timeout 5000 ms
- slow threshold 1000 ms
- failures to DOWN 2
- successes to recovery 3
- reliability target 99.9%
- webhook URL http://webhook-receiver:9000/pulse

Every service must validate that:
slow_threshold_ms < timeout_ms
timeout_ms < check_interval_seconds * 1000


[Prompt 7 - Database models]

Create the SQLAlchemy models for:
- services
- health_checks
- service_state_changes
- incidents
- incident_events
- incident_notes
- notifications

Use database constraints for status values, thresholds, reliability target and
notification event types. Keep every health-check result after it is performed.
The health-check error message is operator-only and must not be stored in public
response objects.


[Prompt 8 - Health-check rules]

Implement the monitoring state machine as a pure function. There should be no
database or HTTP calls inside the state engine.

Use these outcomes:
- 2xx <= 1000 ms: OK_FAST
- 2xx > 1000 ms: OK_SLOW
- non-2xx: FAIL_HTTP
- timeout: FAIL_TIMEOUT
- connection error: FAIL_CONNECTION

Rules:
- 1 failure -> DEGRADED
- 2 consecutive failures -> DOWN
- 3 consecutive successes -> HEALTHY
- DOWN, then one success -> RECOVERING
- another failure while RECOVERING -> DOWN
- slow 2xx counts as a successful check

Write table-driven tests for normal, slow, timeout, random failures, interrupted
recovery and recovery. Do not let a one-off failure open an incident.


[Prompt 9 - Scheduler]

Implement one scheduled task per enabled service. The checks must run
independently with httpx; a slow payments check must not delay claims or
notifications.

Store every result with:
- service ID
- scheduled_at
- started_at
- completed_at
- outcome
- success
- HTTP status
- response time
- operator-only error text
- resulting status

Use the service interval and timeout. A service update must restart its schedule.
Delete or disable must stop it. Add a test that proves slow checking does not
increase the scheduler lag of other services.


[Prompt 10 - Restart and concurrency]

Service state and consecutive counters must survive an application restart.
When Pulse restarts, load the existing counters and open incidents and continue
the schedule from the database.

Because two Pulse containers could accidentally be started, only one instance
should run the scheduler and notifier. Use a PostgreSQL advisory lock.
The second instance should remain API-only and expose its role as standby.

Add restart tests and a test for the standby instance.


[Prompt 11 - Catalogue API]

Build GET, POST and PATCH APIs for the service catalogue.

Catalogue fields:
- name
- description
- health URL
- owner
- criticality
- interval
- timeout
- slow threshold
- failure threshold
- recovery threshold
- reliability target
- enabled
- flaky settings

Name must be unique. Reliability target must be greater than zero and less than
100. Patch operations must preserve fields not included in the request.
Invalid input should return normal validation errors, not a success-shaped response.

Use Pydantic schemas for request validation and SQLAlchemy constraints for final
database protection.


[Prompt 12 - Incident rules]

Implement automatic incident management:

- enter DOWN -> open a service_down incident
- repeated failures while an incident exists -> add an event, do not create a
  duplicate
- enter RECOVERING -> add a recovering event
- three successful checks -> resolve unresolved service_down incidents
- status lifecycle -> OPEN, ACKNOWLEDGED, RESOLVED

Several incidents may be open for the same service. Prevent duplicates using a
unique trigger key based on the service and first failed check. Operators can
acknowledge incidents and add notes.

Ack or notes on a resolved incident must be rejected. Repeated acknowledgement
should be idempotent.


[Prompt 13 - Flaky services]

Add flaky detection for the quotes service.

A flaky service is detected when it records the configured number of failures
inside a rolling failure window. Flaky detection should only move HEALTHY to
DEGRADED or retain DEGRADED. It must not override DOWN or RECOVERING.

Failures while already DOWN should not contribute to flaky detection.
Flaky incidents are optional. Keep flaky_opens_incident off by default until
the product owner confirms they want a separate flaky incident.


[Prompt 14 - Webhook delivery]

Create a notification outbox. Opening or resolving an incident and writing the
notification row must happen in the same database transaction.

The sender should POST to /pulse on the webhook receiver. Send only
incident.opened and incident.resolved events.

Use 4 attempts maximum and backoff of 5, 15 and 45 seconds for timeout, 5xx and
429 responses. Do not retry ordinary 4xx responses. Store every attempt,
HTTP status and delivery error.

The payload must never contain raw internal error text or database/IP details.
It can contain the incident ID, service name, owner, event, status, timestamp
and resolved duration.


[Prompt 15 - Public status API]

Add public status endpoints. Public responses may contain only customer-safe
status and public incident text.

Do not expose:
- internal error messages
- IP addresses
- hostnames
- owners
- operator notes
- response latency
- database information

Create separate Pydantic schemas for public and operator data instead of trying
to filter sensitive strings at the end.

Test with a real down service and text like 10.12.4.7 and a database timeout.
The public response must not contain it.


[Prompt 16 - Reliability metrics]

Implement the reliability calculation as a pure function.

Availability = successful checks / eligible checks * 100.
Only checks actually performed in the window count.
Time before monitoring began is no data, not 100%.
Slow 2xx checks count as successful.

Allowed downtime = 24-hour window minutes * (1 - target / 100).
For 99.9%, that is 1.44 minutes.
Budget remaining = allowed downtime - observed downtime.
Negative budget should be shown as exhausted rather than silently capped.

Support 24-hour and 7-day views. Hand-calculated unit tests are required.


[Prompt 17 - Operator dashboard and metrics]

Build the JSON dashboard summary and metrics endpoints.
The operator can see:
- current service status
- open incidents
- recent incidents
- latest health checks
- 24-hour or 7-day availability
- error budget
- latency
- check success rate

Product metrics must calculate MTTD, MTTA, MTTR, incident count, p50/p95
latency, scheduler lag and webhook delivery success. Explain the timestamps used
for each metric in code and documentation.


[Prompt 18 - Authentication]

Because operator APIs contain internal details, add one demo operator account.
Read the username and password from environment variables. Use a signed,
HttpOnly session cookie.

Require authentication on operator catalogue, incident and metrics endpoints.
Keep public status endpoints anonymous.

Demo credentials can be:
username operator
password pulse-demo

Mark these credentials as demo-only and explain that production should use a
proper identity provider.


[Prompt 19 - Backend-only decision]

The product owner confirmed that the requested frontend is not required. Replace
the UI work with backend JSON APIs. The root route should redirect to /docs.
Remove Jinja or React as a product dependency and document that Swagger is the
operator console.

Do not claim a frontend exists. Public status and dashboard data must still be
delivered through REST APIs.

Write unit and integration tests for:

- incident lifecycle
- duplicate incident prevention
- public data filtering
- availability and error budget

[Prompt 21 - Fix the test database]

The test suite showed duplicate PostgreSQL type names after repeated setup.
Reset pulse_test before each full run, use drop_all carefully and verify
the database is fresh.

Do not treat an infrastructure fixture failure as an application failure.
Once the database is clean, rerun the suite and report actual code failures
separately.


[Prompt 22 - Live acceptance test]

Build the complete stack and run the acceptance tests against the live containers.

Clear the webhook receiver first.

Check the following:
- claims down causes exactly one incident and exactly one opened/resolved pair
- payments slow returns DEGRADED and creates no incident
- flaky quotes behavior returns DEGRADED without an unintended down incident
- Pulse restart keeps history and open incidents
- public status has no internal leak
- active Pulse instance owns the scheduler

Use the real mock services and webhook receiver. Do not replace them with a
mock in acceptance tests.


[Prompt 23 - Incident drill]

Run the fast incident drill. Verify claims goes DOWN and opens an incident,
payments stays DEGRADED, and quotes may alternate while flaky mode is active.

After reset, verify claims resolves and receives the resolved webhook.
Every event should have a matching notification record.
Capture the output and service state for the final review.


[Prompt 24 - Acceptance fix attempt]

During acceptance, four scenarios passed but later scenarios lost the HTTP
connection to Pulse. Check container logs before changing application code.
If Pulse restarted or the test rerendered a container, distinguish a test
environment problem from a crash.

Do not patch the state engine or incident logic solely because a live HTTP
connection was briefly unavailable. Rebuild and health-check Pulse first.
